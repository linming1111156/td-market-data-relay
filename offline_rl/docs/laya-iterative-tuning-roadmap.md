## 路线

### 1. 先在 Kaggle CPU 核对评估

- 输出评估样本的真实标签、预测标签和混淆矩阵，逐条检查类别顺序和 Laya 的 choice 输出。
- 用同一份评估 JSONL 计算 always-flat、base Laya、微调 Laya 的准确率、balanced accuracy、macro-F1 和各类别召回率。
- 验证评估集与训练集按时间完全隔离，并检查校准数据是否与评估数据复用。
- 先完成指标口径核对；核对通过且数据满足实验条件后，Kaggle 微调优先使用 GPU。若 GPU 滚动配额已满、剩余额度不足或无法核实，则切换到 Kaggle CPU，不突破配额上限。所有原始与派生数据、依赖安装、处理、训练、评估、报告和模型产物均在 Kaggle 完成；本机只保存源代码与路线图，不下载或缓存 Laya 数据/运行产物。

### 2. 用 Kaggle CPU 改善数据与标签

- 在 Kaggle CPU 上由 Rust 并行流式读取 Kaggle 输入中的 zstd，报告压缩校验、时间覆盖、缺口、重复、可用特征和分片拒绝原因。中间数据写入 Kaggle `/kaggle/working`；最终报告和模型 bundle 保存为 Kaggle notebook 输出或 Kaggle 私有数据集版本。不得下载到本机。
- 扩大到多个独立市场区间；盘口分片只有在完整性通过后才加入特征。
- 对不同决策周期、持有期、成本门槛和标签分布做离线敏感性分析，保留纯时间切分，避免随机拆分造成泄漏。
- 建立固定版本的数据清单和哈希，使每轮标签与 checkpoint 可复现。

### 3. 建立 CPU 基线与晋级门槛

- 在 Kaggle CPU 比较 always-flat、简单趋势/反转规则、轻量传统分类器和 base Laya。
- 在多个未见时间段报告准确率、balanced accuracy、macro-F1、混淆矩阵、校准度、交易次数、换手和扣除手续费/滑点后的收益及回撤。
- 预先冻结验收规则：模型评估须在多个未见时间段与固定规则基线上报告分类、校准、覆盖、换手及费用/滑点后结果；不以单个 PnL 数字反复调策略或阈值。费用后 PnL 是要保留的真实结果和运行风险指标，不是样本有效性标准，也不是唯一的模型晋级目标。数据/研究轮次即使亏损也照常保留；任何策略或模型的晋级与回滚依据必须预先写定并综合多个未见时段，不能为迎合 held-out 收益而拟合。

### 4. Laya 0.5 持续学习与经验回放（GPU 优先，Kaggle CPU 回退）

- 先用历史标注样本初始化 `Learner`，每条市场状态经未来标签确认后才调用 `feedback`；绝不把模型自己的预测当作正确答案回灌。
- 将 `workdir` 放在 Kaggle 可持久化输出中；反馈服务会把确认时间、状态文本、确认前预测、最终标签、版本与 held/accept/discard/undo 事件追加到 Kaggle 仓库目录之外的 JSONL 审计日志，并随运行报告留存在 Kaggle。每 50 条反馈后由后台训练小头。
- 离线评估也提供 `prequential` 模式：按时间顺序先预测、再回灌该条已实现标签；每 50 条确认反馈后等待所选设备上的更新完成，再评估后续批次。冻结模型和在线更新结果分别报告，避免把未来标签提前用于当前预测。本机不运行 Laya 推理或反馈训练。
- `prequential` 支持通过 `--bundle` 从前一轮 ZIP 恢复已学样本与决策头，并在报告中记录该 bundle 的 SHA-256；未提供 bundle 时才从当前 seed 初始化。
- 调用 `held()` 审核突变或数据异常批次，通过后 `accept()`，误标或坏数据用 `discard()`；误升级可 `undo()` 回滚。
- 每次更新后在固定的多个未见时间段评估；只有候选头稳定胜过 Vega 读者和 CPU 规则基线时才启用该头。
- 保存最近版本及可迁移 ZIP bundle；新运行从工作目录或 bundle 恢复，并继续混入历史经验，避免会话目录丢失状态。

### 5. 优先 Kaggle GPU 微调、持续评估和反馈服务，额度不可用时转 Kaggle CPU

- 通过评估口径和数据质量检查后，优先用可用 GPU 做经典 encoder 微调；每轮只改一个因素，并与 base Laya、当前晋级 checkpoint 及 CPU 基线比较。微调不是自动晋级，仍须满足多时间段和费用后验收标准。
- 每次启动前查询 Kaggle 滚动 7 天 GPU 用量和预留量。若该轮计划会使计划用量超过 27 小时，或额度已耗尽/无法核实，则该轮在 Kaggle 改用 CPU；任何情况不得超过 30 小时硬上限。额度恢复后再回到 GPU 优先调度。本机 CPU 不作为模型运行的回退设备。
- Laya 0.5 `Learner` 的反馈训练、持续评估和反馈服务均优先使用已批准的 Kaggle GPU；额度不足或 CUDA 不可用时回退 Kaggle CPU。它们与经典 encoder 微调分开评估，GPU 不是运行前提。
- 每个实验项目一次只改一个因素，并保留之前晋级的 head/checkpoint。将互相独立的评估或单因素实验拆成多个私有 Kaggle 项目并行运行，缩短验证墙钟时间；不重复跑相同任务来消耗 GPU，也不把大模型微调当作默认递归路径。

### 多 Kaggle 项目并行验证

- 每轮先冻结数据版本、评估切分、模型起点和候选假设，再按互相独立的任务创建多个私有 Kaggle 项目；项目名称和 manifest 使用统一轮次编号及不同实验标签。优先并行运行独立模型/种子、互不重叠的时间段或消融项。
- **GPU notebook 槽位受限时，优先在最多两个已获 GPU 的 notebook 内并行编排多个微调子分支**，而不是为每个子分支再创建 GPU notebook。每个分支使用独立实验配置、随机种子、checkpoint、日志和输出目录；共享只读的已校验输入及 Rust 准备结果，不得共享会互相覆盖的训练状态。分支须在一个矩阵清单中登记假设、单因素改动、预算上限和结果。
- [build_laya_kaggle_finetune_notebooks.py](../scripts/build_laya_kaggle_finetune_notebooks.py) 已生成 MB16/MB32 私有 T4 notebook 的 v8 矩阵方案：每个 notebook 4 个独立 seed 分支、每分支独立 checkpoint/log/output、Rust 准备只运行一次；当前实现使用最多 2 个有界子进程。8 个分支最初各预留 0.5 GPU 小时，整批计划 4 GPU 小时；v7 的实际首分支超时说明该预算/时限需在新探针后重估。启动前须传入新鲜官方 quota 和其他活动/排队 GPU 任务剩余预留小时，并校验 `已用 + 已预留 + 本批计划 <= 27h`。Web UI 多 cell 执行作为另一种候选调度方式，按上方规则实测前不视为可用并发。
- **Web UI 多代码片段并行规则（用户提出，待实测）**：Kaggle GPU notebook 同时槽位最多两个时，下一步微调优先放进这两个 GPU notebook 内，各 notebook 再拆成多个独立子分支，不为每个分支额外申请 GPU notebook。用户记得 Kaggle Web 端可同时运行多个 cell/脚本；将其作为优先验证的编排方法，但当前没有本项目实测证据，不能写成已确认能力。每个 cell 只启动一个隔离子进程，使用独立配置、种子、checkpoint、日志和输出目录，不依赖可变共享 Python 全局变量；只读共享已校验输入和 Rust 准备结果。正式训练前，用 Web UI 在同一 notebook 同时启动两个轻量 cell 探针，记录启动/结束时间、执行状态、kernel/session 标识并确认时间重叠；只有界面显示“运行中”不算证据。若 cell 排队串行，则使用 notebook 内有界子进程调度。所有分支仍共享 notebook 的 GPU、CPU、内存与时限；并发不增加 GPU 配额，也不代表获得独立加速器。确认重叠后先限制同时训练数并观察显存和吞吐，再扩大分支；统一滚动预算按所有分支实际 GPU 用量核算。
- 在共享 GPU 上并发会争用显存和算力。按可用显存及吞吐限制同时训练数，优先通过顺序准备、异步数据处理或短任务错峰隐藏空档；只有确认资源足够时才让多个 GPU 训练步骤同时运行。任一分支 OOM、被抢占或未完成都要单独记为失败/未完成，不能静默丢弃；父 notebook 仍须输出完整分支清单和成功、失败、跳过状态。
- notebook 层面的计划运行时间按其内部所有分支的最坏总 GPU 用量估算，而不是把每个分支各自的 quota 额度相加或忽略。记录父 notebook 的总时长上限、每个子分支预算、实际 GPU 小时和共享准备开销；统一用批次公式核算总预算。若共享资源导致分支串行，预算按串行上界计；若确有重叠，GPU 小时仍按所有分支实际累计用量计。
- 数据准备和 Rust 归档校验只做一次并固化为 Kaggle 数据版本或校验过的输入；各项目只挂载同一只读输入，使用不同 `/kaggle/working` 输出目录，避免重复预处理、覆盖报告或相互污染状态。
- `prequential` 单条时间序列必须保持先预测、后反馈、再更新的顺序；不得把同一序列拆成并行片段后冒充连续学习结果。只有各自从相同冻结 checkpoint 开始、评估边界独立的时间段才可并行，结果合并时保留各段与模型版本信息。
- 并行启动前读取一次新鲜 Kaggle GPU quota，并盘点仍在运行和已排队的 GPU 项目。令 `U` 为滚动 7 天已用时、`r_j` 为已运行/排队 GPU 项目的剩余计划小时、`p_i` 为本批新项目的计划 GPU 小时，则统一调度器必须先核算 `U + sum(r_j) + sum(p_i) <= 27h`，至少留 3 小时余量且不触及 30 小时硬上限。运行中的 v16 也计入 `r_j`；不得让每个项目分别拿完整 27 小时额度。每个项目自己的设备门控不能代替批次总预算核算。
- 为每个 notebook 分配单独的 GPU 时长和总超时；启动后核对实际加速器与运行状态。若 Kaggle 同时运行限制、资源排队或 T4 不可用导致并行 GPU 未实际分配，则排队或按总预算切换 Kaggle CPU，不用本机 CPU，也不突破配额。每个项目完成后立即保存输出并释放槽位，从已预备队列立即启动下一项；不因等齐其他项目结果而空置可用 GPU。
- 流水线规则：首批运行期间就准备下一批 notebook 和 metadata；可用时以 `--no-run` 私有保存，Kaggle 并发槽位释放后立即 push/run。每次结束时先记录结果，再补充路线图和队列状态，保持 GPU 槽位持续有已排队工作。若同时运行上限已满，只预建并排队，不重复启动来突破上限。
- 并行只缩短独立验证任务的墙钟时间，不改变评估口径或晋级门槛；每个项目一旦完成，立即把配置、数据/评估切分、设备、quota、核心指标、费用后净收益、限制及晋级决定追加到本路线图，再启动队列下一项。任何单个项目的成功结果仍须在多个未见时间段与费用后指标上满足路线图门槛，才可晋级。

### 循环式 paper trading 与数据集迭代

- **研究目标与禁止事项**：主目标是沉淀覆盖不同市场状态、来源可追溯、标签完整且质量经过审计的经验数据集，不是把费用后收益调到最好。亏损、盈利和持平都只是结果标签；不能据此删除样本、判定交易无效或单独决定某轮失败。禁止围绕同一 held-out 区间反复改策略、阈值、标签或特征来追求更高收益；held-out 只作冻结方案的一次评估。实验比较服务于数据质量、标签可信度和可复现性，收益指标作为独立描述字段保留，不作为数据集质量目标函数。
- **可行方式**：把“交易→记录→清洗→标签成熟→微调→未见时段测试”作为按轮次运行的 Kaggle 批处理闭环。Kaggle 运行只做模拟/paper trading；不能把同一份历史数据反复回放产生的记录宣称为新行情或独立样本。每轮新生成的数据集必须绑定一个唯一 round ID、输入数据版本、模型/checkpoint 哈希、特征和标签版本、费用/滑点假设及运行代码版本。
- **私有数据集沉淀**：所有轮次统一追加到 Kaggle 私有数据集 `minglinl99/laya-market-paper-trade-experience` 的新版本。每版包含逐决策/模拟交易 JSONL、质量事件 JSONL、版本 manifest、输入/代码/模型哈希、统计报告与清洗计数；不得覆盖旧版。Kaggle notebook 在 `/kaggle/working` 生成并通过 Kaggle API 发布数据集版本；API 凭据只能从 Kaggle Notebook Secret 读取，绝不写入仓库、notebook 源码或日志。本机不接收这些数据或文件。若发布凭据不可用，该轮只能标记为 Kaggle notebook 输出待发布，不能宣称私有数据集已沉淀完成。
- **逐笔先预测后落账**：每条样本只允许使用决策时刻已知的特征；先写入不可变预测/模拟订单事件，再等 15 分钟前瞻期及成交/费用数据完整后补入 outcome、标签和到期时间。禁止用模型预测当作真值回灌。日志至少记录 event/sample ID、时间、round ID、source snapshot、特征哈希、模型版本、动作/概率、置信度、模拟订单与成交/未成交状态、mark 价格、费用、滑点、前瞻收益、标签和校验原因。
- **有效性与盈亏分开**：每条交易样本都保留在版本化数据集中，并带 `record_validity=valid|invalid|unresolved`、`validity_reasons[]`、`execution_status`、`outcome_status`。有效表示时间顺序、来源、字段、哈希、mark/trade 覆盖与费用账本均满足数据契约；未成交、部分成交、过期行情、重复 ID、缺字段、时间倒置、标签未成熟等要分别标记和说明。`profitable|loss-making|flat` 是结果字段，不能作为有效性判定：亏损但完整可信的交易仍是有效样本；坏数据和未成熟样本也不删除，只在训练前按明确状态排除或等待。
- **清洗与建集**：Rust 并行校验/去重、时序及覆盖检查在 Kaggle CPU 执行；修正记录必须保留原始值、修订值、理由和父样本 ID，禁止静默覆盖。每轮保存一个只增不改的 Kaggle 私有数据版本或 notebook output，报告有效/无效/未决条数及各自原因、标签分布、时间缺口、哈希；本机只保存生成器代码和路线图。下一轮读取上一轮已成熟且 `record_validity=valid` 的样本，再追加新一轮记录；无效和未决记录继续保留在数据集但不作为训练标签。
- **反馈、训练与验收**：新一轮只从成熟有效记录构造训练目标；按照时间切分，标签前瞻期设置 embargo，训练/调参/校准不能读取未来 fold。旧 checkpoint 与新候选在多个未见时间段上成对运行，报告分类、覆盖率、模拟成交率、换手、费用/滑点后收益和回撤；费用后亏损不会让样本或数据集失效，也不单独决定研究轮次回滚。模型晋级根据预先冻结的多时段模型/数据质量标准综合判断，避免围绕 held-out 盈亏持续搜参；所有失败实验、亏损交易和已标记无效/未决记录仍保存在 Kaggle 私有数据集版本中。
- **当前数据的边界**：现有 VPS capture 快照只到 2026-11-20，且已知评估段只有两个连续 session。用它们可先建立可复现历史 replay/paper-trading 管道，但产出的策略记录属于同一历史回放，不是新增独立行情。要持续获得真正新样本，需要后续完整 Relay capture 作为新的 Kaggle 输入版本；不完整 sidecar 仍按现有门槛拒绝。Kaggle notebook 是有时限的批处理任务，不能假定一个 notebook 常驻运行；每轮结束写出版本化状态，数据更新或前轮完成后再启动下一轮。
- **逐轮 GPU 安排**：每轮 CPU 清洗与指标审计先完成；只有产生新的可证伪单因素假设后才微调。并行策略仍遵守最多两个 GPU notebook 槽位；可在各自 notebook 内拆为隔离子分支，但所有分支共享配额/资源。新一轮在旧轮仍运行时必须独立冻结数据和评估边界，不能并行处理同一时间序列的 prequential 反馈顺序；统一核算滚动 GPU quota，结果及时追加到本路线图。

### 6. GPU 配额与释放

- 硬上限：任意滚动 7 天 GPU 时间不超过 30 小时；计划预算不超过 27 小时，留出排队和统计误差余量。
- 调度模式：微调、Laya 推理、持续评估和反馈服务优先使用可用 Kaggle GPU；配额已满、剩余额度不满足计划，或无法确认额度时，切换到 Kaggle CPU。每次启动 GPU 前核对滚动配额，任何情况不超过 30 小时；计划不超过 27 小时，留出排队和统计误差余量。数据完整性检查、Rust 合成和传统基线也都在 Kaggle CPU 上运行。
- GPU 只在计划内的模型微调、推理或持续学习期间开启；任务完成或失败后立即停止会话并关闭加速器，确认没有活动 GPU 会话。

### Laya 0.5 设备边界

- Laya 0.5 不是 CPU-only：训练入口有 `--device cuda`，Reader/Learner 调用也接收 device 参数；CPU v15 是 CPU 诊断；新建的 GPU v16 启用 T4，并为持续评估设置 CUDA 优先、额度门控和 Kaggle CPU 回退。
- `laya_market_continuous.py` 的 evaluate、prequential、serve 共用滚动配额门控；`laya_market_feedback_server.py` 使用同一设备选择逻辑，审计记录设备、配额与最长运行时间。经典 encoder 微调入口有 quota-gated CUDA/auto 逻辑，需在 fresh quota check 之后使用。
- 不能把整个流程都迁到 GPU：Rust zstd 校验、数据清洗/标签、CPU 规则与传统基线仍在 Kaggle CPU；Laya/Vega 模型推理或训练才可能使用 GPU。CPU 诊断完成后，若候选实验确需 GPU，先以 `kaggle quota` 查询当前额度，再开启 Kaggle GPU；绝不从本机 CPU 回退。

## Python 性能与内存硬约束

- 适用于本项目全部 Python 脚本。用 Kaggle 上的代表性数据和可复现配置确认 CPU 热点或峰值内存瓶颈后，必须把对应热路径改为 Rust 实现，并在语义允许处使用有界多核并发；不得把已确认的解析、转换、标签、指标或逐行调度热点长期留在 Python。本机不存储或处理 Laya 数据集。
- Python 保留命令行入口、工作流编排和第三方模型库调用。大文件必须流式分块处理，限制并发 worker 和缓存大小；优化目标同时包括更高吞吐和更低峰值 RSS，不得以无界并发换速度。
- `prequential` 同一时间段内的“预测→反馈→更新”顺序不可并行重排。Rust 可并行处理互相独立的时间段、训练种子和文件分片；合并结果前必须维持原有时间隔离与顺序语义。
- 每项 Rust 优化都要记录 Python 基线和 Rust 版本的运行时间、峰值 RSS、worker 数、输入哈希，并核对逐行结果或最终指标一致。只有结果等价且 Rust 版本吞吐更高、峰值 RSS 更低时，才允许替换 Python 热路径；否则继续优化，不得宣称已达成性能目标。
- 当前优先剖析候选是 `laya_vision_prepare.py` 的全量行列表/时间索引构建，以及 `laya_market_continuous.py` 的全量 JSONL 载入和逐条 `Learner.decide`/反馈循环；这些代码路径尚未有代表性多月负载的性能剖析，暂不把它们断言为已确认瓶颈。下一轮在 Kaggle CPU 上先测量，再将确认的瓶颈迁入 Rust 多核流水线；不得把此前本机 CPU 未完成的尝试作为性能基线或模型结果。

## 每轮递归

每轮的全部执行步骤都在 Kaggle：问题假设 → Kaggle CPU 数据诊断并固定数据版本 → 一批已确认反馈 → 建立并行项目矩阵 → 按批次总预算并行 GPU 微调/独立时间段验证（额度不足或无法核实时用 Kaggle CPU）→ 汇总多时间段与费用后指标 → 晋级或回滚 → 更新下一轮假设。输入、临时文件、报告和模型 bundle 均保留在 Kaggle；本机只保存代码和路线图，不下载、缓存、处理或产出 Laya 数据及运行结果。只有决策头在多个未见时间段稳定超过 Vega 与规则基线并通过费用后验收时，才晋级为下一轮起点。
